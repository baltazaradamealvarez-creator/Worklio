# Deploying Worklio on Render

`render.yaml` at the repository root is a [Render Blueprint](https://render.com/docs/blueprint-spec) that
provisions a Node web service and a managed Postgres 16 database.

## 1. Create the Blueprint

In the Render dashboard choose **New → Blueprint**, select this repository and the branch to deploy
(the file must exist on that branch), and fill in the variables marked `sync: false`:

| Variable | Notes |
| --- | --- |
| `APP_URL` | Public URL, e.g. `https://app.example.com`. Defaults to the `onrender.com` URL if empty. Used in emailed links. |
| `RESEND_API_KEY`, `EMAIL_FROM` | Transactional email. The sending domain must be verified in Resend. Use `EMAIL_PROVIDER=console` only for testing. |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | Only when `PAYMENT_PROVIDER=stripe`. Point the Stripe webhook at `/api/webhooks/stripe`. |

`APP_SECRET` and `APP_DB_PASSWORD` are generated by Render.

## 2. What happens on each deploy

1. **Build:** `npm ci --include=dev && npm run build` (generates the Prisma client, builds Next.js).
2. **Pre-deploy:** `scripts/render-predeploy.mjs` creates the restricted `worklio_app` database role,
   then runs `prisma migrate deploy`. Row-level security only protects tenants when the application
   does *not* connect as a superuser or a `BYPASSRLS` role.
3. **Start:** `scripts/render-start.mjs` connects as `worklio_app`, refuses to start if the role could
   bypass RLS, and launches `next start`. If Render does not allow role creation on your plan, it falls
   back to the owner connection (RLS is `FORCE`d on every tenant table, so isolation still applies).

## 3. Create the first platform administrator

After the first successful deploy, open a **Shell** on the web service and run:

```bash
ADMIN_EMAIL=you@company.com ADMIN_PASSWORD='a long passphrase' ADMIN_NAME='Your Name' \
  npx tsx scripts/create-platform-admin.ts
```

Sign in at `/login`; you land on `/platform`, where you create companies and invite their owners.
Do **not** run `prisma/seed.ts` in production — it creates demo accounts with known passwords.

## File storage

The Blueprint mounts a 10 GB persistent disk at `/var/data` and stores uploads under `/var/data/files`.
Persistent disks pin the service to one instance. To scale horizontally, set `STORAGE_DRIVER=s3` and the
`S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` (and optionally `S3_ENDPOINT`) variables,
and remove the `disk:` block.

## Backups and operations

* Use a paid Postgres plan (the Blueprint defaults to `basic-256mb`) so point-in-time recovery is available;
  size it up as data grows.
* Monitor `/login` (the health check) and the Render logs. Audit logs are append-only inside the app
  (`/activity` for companies, `/platform/audit` for platform actions).
